# MindFlow Storage & Maintenance Guide

This document outlines the strict guidelines for database storage management, safe pruning practices, and expected lifecycle behaviors within the MindFlow Supabase project.

## 1. Protected Tables (NEVER TOUCH)

The following tables contain core production application data, user states, and critical configuration. **Under no circumstances should manual `DELETE`, `TRUNCATE`, or `VACUUM FULL` commands be run against these tables.**

*   **`public.questions`**: Core Quiz Data.
*   **`public.synonym`**: Core Vocabulary/Dictionary Data.
*   **`public.idioms`**: Phrase Data.
*   **`public.reels`**: Media Data.
*   **`public.user_active_sessions`**, **`public.quiz_sessions`**: Active user state.
*   **`auth.*`**: Supabase Authentication schema.
*   **`storage.*`**: Supabase Storage object mapping schema.

*(Note: Application data relies on soft-deletes and tombstone mechanisms, managed entirely via application code/RPCs, never via raw SQL maintenance scripts).*

## 2. Safe-to-Prune System Tables

The following tables are internal logs generated by Supabase extensions. They are actively managed by the automated maintenance system.

*   **`net._http_response`**: Internal logs for Edge Function and webhook requests.
*   **`cron.job_run_details`**: Execution history for `pg_cron` scheduled jobs.

## 3. The Nightly Cleanup Mechanism

To prevent the system log tables from growing infinitely, an automated, idempotent function (`maintenance.prune_system_logs()`) is scheduled via `pg_cron` (`maintenance-prune-system-logs`) to run daily at 03:00 AM UTC.

**How it works:**
1.  It iterates in small batches (5,000 rows at a time).
2.  It deletes HTTP and Cron logs older than their configured retention window (default 7 days).
3.  The 7-day window ensures that dashboard RPCs (`get_enrichment_dashboard_metrics`) have enough recent data to calculate pipeline health without hoarding gigabytes of historical logs.

## 4. Expected Storage Behavior

PostgreSQL uses Multi-Version Concurrency Control (MVCC).

*   **Files do not shrink immediately.** When the nightly cleanup deletes rows, the physical storage reported by Supabase will not immediately drop.
*   **Autovacuum reclaims space.** The built-in PostgreSQL `autovacuum` daemon will scan the table and mark the deleted rows as "Free Space".
*   **Space is Reused.** Future logs will be written into this pre-allocated free space. The file size will plateau (e.g., stabilizing at ~136 MB for `cron.job_run_details`), preventing unbounded growth.

## 5. Emergency Intervention: `VACUUM FULL`

`VACUUM FULL` rewrites an entire table, blocking all read and write queries to that table while it runs.

**It is strictly prohibited in normal operations.**

It should **ONLY** be considered if ALL of the following conditions are met:
1.  The overall database volume is at > 90% critical capacity.
2.  A diagnostic check (see `SYSTEM_MAINTENANCE.md`) proves a massive amount of free space exists in a bloated table.
3.  A formal maintenance window has been scheduled, acknowledging that the application (or background queues) will experience locking/outages during the operation.
